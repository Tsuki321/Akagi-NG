Akagi Android is a native Android 16 application with Mahjong Soul hosted in its own WebView and the bundled Mortal v4 four-player and three-player models executed on the device. It targets the Galaxy A54's ARM64 architecture; the APK also contains x86_64 libraries for emulator validation.

The game fills the screen. The default advice chip has a 34 dp visible surface and at least a 48 dp touch target. Tap to expand; hold and drag to move it within the upper part of the screen. This keeps the player's hand and lower game controls available. Settings, account help and model checks appear only when opened. Android's normal first-use fullscreen explanation appears once and can be dismissed with Got it.

Use Mahjong Soul's Yostar sign-in. For an existing Google-based account, first bind an unused Yostar account using Mahjong Soul's account settings, then use that Yostar account here. Check that the player ID is the same. The app explains this route when Google authorization is selected; it does not copy another browser's session. A live account and complete authenticated match have not been used in development tests.

**Implementation.** `android/` contains the Kotlin/Compose app. The browser installs a document-start WebSocket observer before navigation. Binary payloads, connection identity and document sequencing pass to the Kotlin Liqi decoder and MJAI adapter. `AnalysisViewModel` owns a bounded, ordered processing worker and discards advice after a capture gap, navigation, sent operation, or invalid state. `native/` supplies the ported rules, legal actions, observation encoders and JNI. ONNX Runtime runs the local models, with deterministic FP32 CPU inference and shared model resources for riichi lookahead.

The entire game update is applied before inference. A draw and its dora announcement, or a discard and its reach payment, form one transaction. This keeps model inputs current and preserves pending ron/chankan opportunities. Replay advances historical state without running inference at each historical decision.

Four-player rules were ported from pinned Mortal v4 source. The three-player deployment layout was reconstructed and checked against the actual bundled `libriichi3p` binary, including its historical normalization, ranking and call-history behavior. Source provenance, licenses and reproducible adapter patches are committed. The mobile runtime contains neither a Python interpreter nor desktop native libraries.

**Validation.** Builds and compilation run exclusively in GitHub Actions. The Android workflow performs:

- Native rules tests, transaction tests and observation/action comparisons with the original desktop binaries.
- Export of both actual bundled checkpoints and comparison of ONNX scores and selected actions with PyTorch.
- Kotlin protocol tests using serialized Liqi messages generated by the original Python decoder, including red fives, melds, kita, sequence gaps and reconnect history.
- Android 16 emulator tests at 1080×2340 / 420 dpi and 720×1600 / 320 dpi, covering physical game taps, fullscreen bounds, chip movement, settings/Back, account help, large text, rotation, cookies, renderer recovery and stale-advice clearing.
- Real loopback WebSocket-to-WebView-to-protocol-to-native-to-model-to-UI tests for both player counts, including corruption, disconnection and reconnection replay.
- On-device model score comparisons, saved-hand replay, foreground recomputation and dora/reach-payment transaction tests.
- Interaction stress, screenshots and measurements, plus a separate launch of the public Mahjong Soul site.
- ELF and APK 16 KB alignment checks for every packaged native library.

The signed-release job runs only after the emulator jobs pass. It verifies APK signatures and native alignment, installs the production APK in an Android 16 emulator, runs the real model and native saved-hand checks through its settings UI, and tests reinstalling the same signed package.

Screenshots containing `fixture` show a deterministic test table; files named `public-game` or `release-game` show the actual online game page. Images containing `live_3p` or `live_4p` show real local inference from serialized protocol messages delivered by an emulator-loopback server. They are not authenticated online matches.

**Practical limits.** Emulator timings are not Galaxy A54 performance measurements. Real-device heat, battery use and long sessions still need measurement on the phone. The browser observer covers document and allowed-frame WebSockets; arbitrary worker-created sockets are not advertised as supported. Unknown game variants and incomplete reconnect histories suppress advice until the state can be reconstructed. Current model support covers the bundled v4 DQN models; arbitrary checkpoints and alternate model families require a compatible export and validation.

**Build outputs and recovery.** Use the `Akagi-Android-16` artifact from a successful Android workflow for the signed installable APK. `android-apks` is the debug/instrumentation pair. Model parity reports, emulator screenshots and measurements are separate artifacts. The signing identity is stored in the fork's encrypted Actions secrets, with a recovery copy under the ignored local `artifacts/signing/` directory. Keep that recovery copy private and backed up; retaining the same signing identity allows updates to preserve app data.
